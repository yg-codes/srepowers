# Safety Validator

## Overview

Review proposed infrastructure commands before execution to catch dangerous operations. Acts as a safety net to prevent accidental data loss or service disruption.

**Core principle:** Explicit confirmation for destructive operations prevents accidents.

**Announce at start:** "I'm using the safety-validator skill to review these commands before execution."

## When to Use

**Always for:**
- Destructive operations (delete, remove, drop)
- Broad-scope operations (wildcards, "all", "*")
- Production environment changes
- Irreversible operations
- Commands generated by automation

**Use before:**
- Executing generated commands
- Running bulk operations
- Applying changes to production
- Executing unfamiliar commands

## Risk Classification

### 🔴 Critical Risk - Block Without Explicit Confirmation

| Pattern | Example | Why Dangerous |
|---------|---------|---------------|
| `rm -rf /` | `rm -rf /data` | Recursive deletion from root |
| `kubectl delete all` | `kubectl --context <context> delete all --all-namespaces` | Deletes everything |
| `DROP DATABASE` | `DROP DATABASE production` | Irreversible data loss |
| `terraform destroy` | `terraform destroy -auto-approve` | Destroys all infrastructure |
| `dd if=/dev/zero` | `dd if=/dev/zero of=/dev/sda` | Overwrites disk |

### 🟠 High Risk - Require Typed Confirmation

| Pattern | Example | Why Dangerous |
|---------|---------|---------------|
| `kubectl delete` | `kubectl --context <context> delete deployment api` | Deletes running workloads |
| `aws ec2 terminate` | `aws ec2 terminate-instances` | Destroys instances |
| `docker system prune` | `docker system prune -a` | Removes all containers/images |
| `git push --force` | `git push --force origin main` | Overwrites history |
| Database modifications | `ALTER TABLE DROP COLUMN` | Schema changes |

### 🟡 Medium Risk - Warn and Confirm

| Pattern | Example | Why Caution |
|---------|---------|-------------|
| `kubectl apply` | `kubectl --context <context> apply -f production/` | Changes production state |
| `terraform apply` | `terraform apply` | Modifies infrastructure |
| Package removal | `apt remove` | Removes dependencies |
| Service restart | `systemctl restart` | Causes brief outage |

### 🟢 Low Risk - Proceed with Log

| Pattern | Example | Notes |
|---------|---------|-------|
| `kubectl get` | `kubectl --context <context> get pods` | Read-only |
| `terraform plan` | `terraform plan` | Non-destructive |
| `ls`, `cat`, `grep` | `ls -la` | Safe read operations |

## The Validation Process

### Step 1: Parse Commands

Break down compound commands:

```bash
# Compound command
kubectl --context <context> delete deployment api && kubectl --context <context> delete service api

# Parsed as:
# 1. kubectl --context <context> delete deployment api
# 2. kubectl --context <context> delete service api
```

### Step 2: Pattern Matching

Check each command against risk patterns:

```python
# Example pattern matching logic
RISK_PATTERNS = {
    'critical': [
        r'rm\s+-rf\s+/',
        r'kubectl\s+delete\s+all',
        r'DROP\s+DATABASE',
        r'terraform\s+destroy',
    ],
    'high': [
        r'kubectl\s+delete',
        r'aws\s+.*\s+terminate',
        r'docker\s+system\s+prune',
        r'git\s+push\s+.*--force',
    ],
    'medium': [
        r'kubectl\s+apply',
        r'terraform\s+apply',
        r'systemctl\s+restart',
    ],
}
```

### Step 3: Risk Assessment

```bash
# Example assessment output

=== Safety Validation Report ===

Command: kubectl --context <context> delete deployment api-server -n production

Risk Level: 🔴 HIGH
Category: Workload Deletion
Impact: Service outage for api-server in production

Why this is dangerous:
- Deletes running deployment
- Causes immediate service outage
- Data in memory will be lost

Verification questions:
- [ ] Is this deployment no longer needed?
- [ ] Is traffic routed elsewhere?
- [ ] Is data backed up/persisted?

Safe alternatives to consider:
1. Scale to zero: kubectl --context <context> scale deployment api-server --replicas=0
2. Drain pods: kubectl --context <context> drain --ignore-daemonsets
3. Apply maintenance page first

Rollback plan:
kubectl --context <context> apply -f api-server-deployment.yaml  # Reapply if needed

Type 'delete-api-server-production' to confirm execution:
```

### Step 4: Confirmation

Require typed confirmation for high/critical risk:

```bash
# Critical risk - require exact phrase
read -p "Type the confirmation phrase exactly: " confirmation
if [ "$confirmation" != "delete-api-server-production" ]; then
    echo "Confirmation mismatch. Aborting."
    exit 1
fi
```

## Validation Rules

### Kubernetes Commands

```yaml
rules:
  - pattern: "kubectl delete.*--all"
    risk: critical
    message: "Deleting all resources of a type"

  - pattern: "kubectl delete.*-n.*(prod|production)"
    risk: high
    message: "Deleting production resources"

  - pattern: "kubectl delete.*deployment"
    risk: high
    message: "Deleting deployment will cause outage"

  - pattern: "kubectl apply.*-f.*prod"
    risk: medium
    message: "Applying changes to production"
```

### Terraform Commands

```yaml
rules:
  - pattern: "terraform destroy"
    risk: critical
    message: "Will destroy all managed infrastructure"

  - pattern: "terraform apply.*-auto-approve"
    risk: high
    message: "Auto-approve bypasses plan review"

  - pattern: "terraform apply"
    risk: medium
    message: "Will modify infrastructure"
```

### Database Commands

```yaml
rules:
  - pattern: "DROP\s+(DATABASE|TABLE)"
    risk: critical
    message: "Irreversible data deletion"

  - pattern: "DELETE\s+FROM"
    risk: high
    message: "Data deletion without WHERE clause?"

  - pattern: "ALTER\s+TABLE.*DROP"
    risk: high
    message: "Schema modification - data may be lost"
```

### File System Commands

```yaml
rules:
  - pattern: "rm\s+-rf\s+/"
    risk: critical
    message: "Recursive deletion from root"

  - pattern: "rm\s+-rf"
    risk: high
    message: "Recursive force deletion"

  - pattern: ">\s+/etc/"
    risk: high
    message: "Modifying system configuration"
```

## Safe Alternatives

### Instead of Delete

| Dangerous | Safer Alternative |
|-----------|-------------------|
| `kubectl delete deployment` | `kubectl --context <context> scale deployment --replicas=0` |
| `rm -rf /data` | `mv /data /data.backup.$(date +%s)` |
| `DROP TABLE` | `RENAME TABLE old_table TO old_table_backup` |
| `terraform destroy` | `terraform plan -destroy` (review first) |

### Instead of Force

| Dangerous | Safer Alternative |
|-----------|-------------------|
| `git push --force` | `git push --force-with-lease` |
| `kubectl apply --force` | `kubectl --context <context> apply` (normal) |
| `rm -f` | `rm -i` (interactive) |

## SRE Principles

### Safety First
- Block critical operations without explicit confirmation
- Suggest safer alternatives
- Require rollback plans for destructive operations

### Structured Output
- Present risk assessment in clear format
- Use consistent risk levels (🔴🟠🟡🟢)
- Show specific reasons for warnings

### Evidence-Driven
- Reference specific command patterns
- Show impact analysis
- Document why operation is risky

### Audit-Ready
- Log all validation decisions
- Record confirmation phrases used
- Track who approved risky operations

### Communication
- Explain risk in business terms
- Suggest alternatives clearly
- Provide rollback instructions

## Example Workflows

### Safe Deletion Workflow

```bash
# Proposed command
kubectl --context <context> delete deployment legacy-api -n production

# Safety validator intervenes:
# 🔴 HIGH RISK: Deleting production deployment
#
# Suggested alternative:
# kubectl --context <context> scale deployment legacy-api --replicas=0 -n production
#
# This keeps the deployment but scales to zero pods.
# You can scale back up if needed.
#
# Or type 'delete-legacy-api-production' to proceed with deletion.

# User chooses safer alternative:
kubectl --context <context> scale deployment legacy-api --replicas=0 -n production

# Verify:
kubectl --context <context> get deployment legacy-api -n production
# Shows 0/0 replicas - safe to delete now if confirmed not needed
```

### Bulk Operation Workflow

```bash
# Proposed command
kubectl --context <context> delete pods --all -n staging

# Safety validator:
# 🟠 HIGH RISK: Deleting all pods in namespace
#
# Impact: All services in staging will restart
# Duration: 30-60 seconds outage per service
#
# Are you sure? Consider:
# - Are you trying to restart pods? Use 'kubectl --context <context> rollout restart' instead
# - Are you cleaning up? Use label selectors for specific pods
#
# Type 'delete-all-staging-pods' to confirm:
```

## Red Flags

**Never bypass validation when:**
- Command was generated by untrusted source
- Operating on production
- Deleting data
- Modifying critical infrastructure
- You're tired or under pressure

**Always require validation for:**
- Automated scripts
- Bulk operations
- First-time operations
- Operations at 3 AM

## Limitations

**Safety validator cannot:**
- Prevent all accidents (human judgment required)
- Understand business context
- Predict all side effects
- Replace proper testing

**Not a substitute for:**
- Code review
- Testing in staging
- Backup procedures
- Change management process
